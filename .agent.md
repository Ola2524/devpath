6. Non-Negotiable Rules
These rules are not suggestions. They exist because breaking them causes production incidents. If a rule seems wrong for a specific case, stop and ask — do not silently bypass it.

6.1 TypeScript Rules
Strict mode is always on. Never disable it.

any is banned. Use unknown and narrow it with type guards.

@ts-ignore is banned. Use @ts-expect-error with a comment if truly necessary.

ESM only. import / export. Never require.

Import paths end in .js (even though files are .ts) — required for ESM + TS.

Type-only imports use import type { X } from "...".

6.2 Database Rules — N+1 Prevention
The single most common performance bug is N+1. Never write it.

NEVER await a Prisma call inside a loop over DB records.

❌ Anti-pattern (N+1):

ts
const matches = await prisma.match.findMany({ where: { userId } });
for (const m of matches) {
  const job = await prisma.job.findUnique({ where: { id: m.jobId } });
  // ...
}
✅ Fix — use include, select, or where: { id: { in: [...] } }:

ts
const matches = await prisma.match.findMany({
  where: { userId },
  include: { job: { include: { skills: true } } },
});
NEVER await inside map / forEach / Promise.all over DB records unless batching is intentional and documented.

✅ Batch when needed:

ts
const jobIds = matches.map((m) => m.jobId);
const jobs = await prisma.job.findMany({ where: { id: { in: jobIds } } });
ALWAYS add an index for any column used in where, orderBy, or relation joins. Update schema.prisma with @@index([column]).

ALWAYS use select to limit returned fields. Never return passwordHash, tokens, or internal fields.

$queryRaw is banned unless using tagged templates (parameterized):

ts
// ❌ Never
prisma.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`);

// ✅ Always
prisma.$queryRaw`SELECT * FROM users WHERE email = ${email}`;
6.3 Security Rules
ALWAYS validate req.body, req.query, and req.params with Zod before use. Use the validate middleware.

ts
router.post(
  "/login",
  validate({ body: loginSchema }),
  authController.login
);
ALWAYS use requireAuth middleware on protected routes. Never trust client-provided userId.

❌ Never:

ts
const user = await prisma.user.findUnique({ where: { id: req.body.userId } });
✅ Always:

ts
const user = await prisma.user.findUnique({ where: { id: req.user.id } });
NEVER log objects that may contain secrets.

❌ logger.info(user) — may include passwordHash

✅ logger.info({ userId: user.id, email: user.email }, "user logged in")

NEVER expose passwordHash, tokens, or secrets in any response. Use select to exclude them.

NEVER trust user input in raw SQL (see 6.2.5).

Auth endpoints MUST be rate-limited. Login, register, password reset — all of them.

JWTs MUST use HS256 or RS256. Never none. Never trust the alg header from the token — verify it.

Cookies MUST be httpOnly, secure (in prod), and sameSite: 'lax'.

CORS MUST be whitelisted. Never cors() with no options in production. Use CORS_ORIGIN env var.

Never return internal error messages to clients. The errorHandler middleware handles this. Throw AppError, let middleware format it.

Secrets MUST come from env vars, never hardcoded. And .env MUST never be committed.

Passwords MUST be hashed with bcrypt (cost factor 12) before storage. Never store plaintext.

6.4 Error Handling Rules
NEVER throw new Error(...) in route handlers. Throw AppError (or its factories: BadRequest, NotFound, Unauthorized, etc.).

NEVER use console.log, console.error, console.warn, console.debug. Use logger.info/warn/error/debug.

ALWAYS log with context:

ts
logger.error({ err, userId, jobId }, "pipeline failed");
Not:

ts
logger.error("pipeline failed"); // missing context
Never bypass the error handler. All errors flow through errorHandler.ts.

6.5 Testing Rules
Every new endpoint MUST have an integration test (using supertest).

Every service function with branching logic MUST have unit tests.

Tests MUST pass in CI before merge.

Test files live next to the code as <name>.test.ts or in __tests__/.

Never test implementation details — test behavior and contracts.

6.6 Dependency Rules
NEVER add a new dependency without asking. The dependency tree is deliberately minimal.

If a task seems to require a package, stop and propose it with justification.

Prefer Node built-ins (crypto, fs/promises, node:url) over packages.

Prefer existing packages over new ones if they solve the problem.

6.7 Commit Rules
Follow Conventional Commits:

text

Examples:

node_modules/

dist/

Half-finished features

8. Working Rules for Agents
Read the code before writing. Check existing patterns in src/modules/.

Never add a dependency without asking.

Run pnpm typecheck before declaring a task complete. Fix all errors.

Never commit .env, secrets, or node_modules.

Never bypass the error handler. Throw AppError, let middleware format it.

Never use any. Use unknown + type guards.

Never use console.log. Use logger.

Never write N+1 queries. See §6.2.

Never trust client input. Validate with Zod. Read req.user.id for identity.

Prefer small, focused changes over large refactors.

Update AGENTS.md if you change architecture, conventions, or commands.

When in doubt, ask. Do not assume. Do not silently bypass rules.
